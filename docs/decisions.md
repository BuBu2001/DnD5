# Решения по программной реализации (Приложение Б, п. Б.3 ТЗ DOC-04)

Документ фиксирует ключевые архитектурные и технологические решения, принятые
при реализации движка V0.4. Формат записи: контекст → решение → альтернативы →
последствия. Нумерация DR-XX сквозная; новые решения добавляются в конец.

---

## DR-01. Технологический стек: SDL2 + OpenGL 3.3 Core с headless-режимом

**Контекст.** Таблица 4.16 ТЗ DOC-04 предписывает SDL2 и OpenGL 3.3 Core.
При этом модульные и интеграционные тесты (раздел 8) должны выполняться в CI
без графической подсистемы, а модуль правил — собираться без SDL/GL (E-D11).

**Решение.** Опция CMake `DND_WITH_SDL2` (по умолчанию OFF). При ON слой
платформы/отрисовки/звука использует SDL2, SDL2_mixer и OpenGL 3.3 Core
(загрузка функций — собственный `render/gl_loader`, проверка отсутствующих
функций — `gl_function_loader_reports_missing`). При OFF (или если SDL2 не
найден в системе) собирается headless-вариант: `platform::Window` без окна,
`render::SpriteBatch` с программным растеризатором в CPU-буфер, звук — заглушка.
Ядро (`engine/core`, `engine/ecs`, `engine/scene`) и `rules` от опции не зависят.

**Альтернативы.** (1) GLFW + GLAD — отклонено: ТЗ предписывает SDL2;
(2) только SDL2-рендерер (SDL_Renderer) — отклонено: ТЗ требует OpenGL 3.3 Core
и собственный батчинг (E-D05).

**Последствия.** Один код тестов исполняется и в CI, и на машине разработчика;
расхождение поведения windowed/headless контролируется тестами
(`sprite_batch_renders`, `ui_letterbox_does_not_cover_scene`, оконный прогон
`game --smoke` с метриками кадров).

## DR-02. Разбор JSON: собственный `core::JsonValue` вместо nlohmann/json

**Контекст.** Таблица 4.16 допускает nlohmann/json, но библиотека на V0.4 не
подключена (каталог `third_party/` — заготовка); данные игры — конверт
`{$schema, schema_version, id}` плюс тело (п. 4.5.3), т.е. разбор нужен
ограниченного подмножества JSON.

**Решение.** Реализован `engine/core/json_value.{h,cpp}` — рекурсивный
JSON-парсер (null/bool/number/string/array/object), доступ по указателю
`get_ptr`, строгая диагностика ошибок с позицией. Валидация конверта и схем —
`tools/json_validator`.

**Альтернативы.** (1) nlohmann/json через FetchContent — отклонено: зависимость
от сети при сборке, лишний вес при текущих потребностях; (2) RapidJSON —
то же. Подключение nlohmann/json остаётся допустимым расширением (таблица 4.16),
интерфейс загрузчика допускает замену реализации без правки модулей.

**Последствия.** Нулевые внешние зависимости сборки; `json_loader_invalid_does_not_crash`
гарантирует безопасность на повреждённых данных (FR-E34).

## DR-03. Шрифты: процедурный растровый атлас, без FreeType/SDL_ttf

**Контекст.** FR-E52 требует текстовую подсистему; DOC-04 допускает stb/SDL_ttf.
Для интерфейса на фиксированной сетке 1280×720 (UI-E02) достаточно одного
шрифта с известными метриками.

**Решение.** `platform::FontAtlas` запекает глифы процедурно
(`scripts/gen_font_table.py` + `scripts/font_glyph_strokes.py` генерируют
таблицу штрихов), ячейка 16×32 px, cap height 19.6923 px, смещение базовой
линии 3/13 ячейки — метрики соответствуют Verdana-подобному начертанию из
п. Г.9. Атлас — одна RGBA-текстура, собирается за один вызов `bake()`
(≈50 мс, бенчмарк «прогрев шрифтового атласа»).

**Альтернативы.** SDL_ttf/FreeType — отклонено: внешняя зависимость,
недетерминированный растр (риск для golden-тестов), избыточно для одного шрифта.

**Последствия.** Полная детерминированность текста; `draw_text` принимает
цвет, масштаб и выравнивание (контракт п. Г.10 проверен тестом
`primitives_and_text_contract`). Добавление нового начертания — генерация новой
таблицы штрихов, код не меняется.

## DR-04. ECS-lite: sparse-set хранилище + буфер отложенных команд

**Контекст.** Подраздел 4.1.6 требует ECS с сущностями {index, generation},
компонентами-данными и системами. Системы во время итерации создают/удаляют
сущности (бой, эффекты) — прямая модификация хранилища в обходе недопустима.

**Решение.** `ComponentStorage<T>` — разреженное множество (sparse set):
плотный массив компонентов + разреженный индекс index→позиция; удаление O(1)
swap-and-pop. `EntityId{index, generation}` — поколение инкрементируется при
переиспользовании индекса, обращение к мёртвой сущности отсекается. Изменения
структуры внутри кадра выполняются через `CommandBuffer`
(`ecs_command_buffer_deferred`), применяются между системами.

**Альтернативы.** (1) `std::map<EntityId, T>` (каркас V0.2) — отклонено:
O(log n) итерация, плохая локальность; (2) чистый archetypal ECS (flecs-стиль) —
избыточен для масштаба задачи (сотни сущностей).

**Последствия.** Создание сущности ~0.7 млн/с, итерация view ~1.2 млн/с
(бенчмарки, Debug) — запас над NFR-E01/E02. Компоненты-обёртки над типами
`rules::*` хранятся в `game/`, движок их не знает (E-D01).

## DR-05. ГСЧ: `SeededRandomProvider` (xoshiro256**), весь рандом — инъекция

**Контекст.** E-D07/FR-K102 запрещают прямой вызов генераторов из игрового кода;
все броски проходят через `DiceRoller` с инжектированным `IRandomProvider`;
требуется воспроизводимость (золотой эталон, seed 42) и сериализация состояния
(FR-K105).

**Решение.** `IRandomProvider{ next_u64(), state()/restore() }`; боевая
реализация — xoshiro256** с explicit seeding; состояние — 4×u64, сериализуется
в сохранение (`rng_determinism_and_state_roundtrip`). Криты/осечки вычисляются
по натуральному кубику внутри `DiceRoller` (`attack_resolution_critical_and_fumble`),
бонус +5 к броску атака не получает (`dice_no_flat_plus_five`).

**Альтернативы.** `std::mt19937` — отклонено: реализация нестандартна между
компиляторами (риск расхождения золотого эталона); LCG — слабый период для
длительных кампаний.

**Последствия.** Бит-в-бит воспроизводимость между платформами и сборками;
подмена провайдера в тестах тривиальна.

## DR-06. Связка engine↔rules: адаптер и DTO, событийная шина

**Контекст.** E-D01: движок не знает правил; E-D12: UI получает только DTO.
Боевая сцена должна отображать разбор атаки (формулы, слои модификаторов)
и реагировать на события правил.

**Решение.** `game/adapters/rules_adapter`: принимает запросы UI (клик по
цели), вызывает `rules::*`, публикует результаты через `engine::EventBus`
(`rules_adapter_publishes_events`) и конвертирует `rules::RollResult`/
`DamageResult` в DTO для UI (`dto_conversion_for_ui`,
`ui_widgets_show_full_breakdown`). UI-виджеты (`engine/ui/`) не включают
заголовки `rules/` — проверяет `scripts/check_includes.py` (E-D02).

**Альтернативы.** Прямые вызовы rules из UI — запрещены ТЗ; шаблонизация
движка типами правил — нарушила бы E-D11.

**Последствия.** Направление зависимостей `game → {engine, rules}` сохраняется;
модуль правил тестируется изолированно (22 кейса `tests_rules` без SDL/GL).

## DR-07. Данные: JSON-конверт `{$schema, schema_version, id}`, инструменты валидации

**Контекст.** П. 4.5.3: все данные (карты, предметы, бестиарий) — версионируемые
JSON-документы; DATA-E05 — виртуальные пути `assets:/`.

**Решение.** Каждый документ содержит конверт; схемы описаны в
`docs/gost/data_formats.md` (генерирует `tools/schema_gen`, 10 схем),
идентификаторы схем — в `generated/schema_ids.h`. Загрузка —
`resource::JsonLoader` через `VirtualFileSystem` (кэш `ResourceCache`,
FR-E68). Валидация на стороне инструмента: `tools/json_validator`
(конверт+схема+ссылки), `tools/map_validator` (проходимость, слои, объекты),
`tools/asset_packer` (упаковка атласов с padding/border).

**Альтернативы.** XML (tinyxml2) — допускается ТЗ для конфигов, для игровых
данных отклонено в пользу JSON (единый парсер, схема-валидация); бинарные
данные — отклонено: нечитаемы инструментами моддинга (FR-E55).

**Последствия.** Повреждённый документ не роняет движок
(`json_loader_invalid_does_not_crash`); миграция версий сохранений —
`save_version_migration`.

## DR-08. Сборка и качество: CMake-пресеты, /MT, -Werror, статические проверки

**Контекст.** NFR-E12 (предупреждения как ошибки), NFR-E14 (статическая CRT
/MT в MSVC), п. Г.11 (цели сборки), требования переносимости MSVC/GCC/Clang.

**Решение.** Корневой CMakeLists: цели `engine`, `rules`, `game`, `tests`,
`tools`, `benchmarks`; пресеты `windows-msvc-debug/release` (MultiProc, /MTd|/MT)
и `linux-gcc-debug/release`; `-Wall -Wextra -Werror` на GCC/Clang, `/W4 /WX` на
MSVC; C++20 без расширений. Дополнительно к компилятору — статические проверки:
`scripts/check_includes.py` (изоляция слоёв NFR-E10/E-D01/E-D02) и
`scripts/hdrcheck.sh` (самодостаточность заголовков).

**Альтернативы.** Bazel/MSBuild — отклонено: ТЗ предписывает CMake ≥3.20.

**Последствия.** Сборка MSVC 19.44 и GCC 12 проходит без предупреждений;
`/MT` устраняет зависимость от redistributable (NFR-E14).

## DR-09. Тестирование: пять уровней + золотой эталон + бенчмарки с порогами

**Контекст.** Раздел 8 ТЗ: модульные (табл. 8.2), интеграционные (табл. 8.3),
золотые значения (п. 8.4), бенчмарки (табл. 8.4).

**Решение.** Пять ctest-целей: `tests_rules` (механики D&D), `tests_engine`
(ядро+ECS+UI), `tests_platform` (окно/ввод/рендер/шрифты), `tests_integration`
(загрузка, сохранения, вертикальный срез боя — Приложение Д), `tests_golden`
(сверка с `tests/golden/golden_values.txt`, seed 42). Бенчмарки — отдельный
бинарник `tests/benchmarks` с CLI `--assets`, `--repeats`, `--strict`
(ненулевой код при просадке ниже порога); пороги — ниже целевых NFR с запасом
на Debug-сборку и программный растеризатор CI.

**Альтернативы.** GoogleTest — отклонено в пользу header-only Catch2
(табл. 4.16); бенчмарки внутри ctest — отклонено: время прогона нестабильно,
пороговые проверки вынесены в `--strict`-режим для отдельного запуска.

**Последствия.** 58 кейсов / 957 проверок на V0.4.3; регрессия
производительности ловится одной командой
`./build/tests/benchmarks --assets assets --strict`.

## DR-10. Каркас тестов: Catch2-совместимый микро-фреймворк до подключения библиотеки

**Контекст.** Таблица 4.16 фиксирует Catch2 (BSL-1.0). На V0.4 библиотека в
`third_party/` не внесена, а тесты нужны с этапа M0.

**Решение.** `tests/test_harness.h` — микро-каркас с тем же набором макросов
(`TEST_CASE`, `SECTION`, `REQUIRE`, `REQUIRE_FALSE`, `CHECK`, `INFO`) и
реестром кейсов; переход на Catch2 выполняется заменой заголовка на
`<catch2/catch_all.hpp>` и подключением `Catch2::Catch2WithMain` — исходный
код тестов не меняется.

**Альтернативы.** GoogleTest — отклонено (нет в таблице 4.16); vendoring
Catch2 single-header — запланирован, отложен до появления потребности в
BDD-секциях и генераторах.

**Последствия.** Тесты не зависят от сети при сборке; статистика прогонов
(кейсы/проверки) печатается в формате, близком к Catch2.
